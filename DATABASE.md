# Database Design

## Status

The initial SQLite schema is implemented in Drizzle. The first generated migration is applied to the local development database. The temporary local Admin account, Blindly Digital employee account, Client Company Owner account, demo client company, eleven canonical roles, 75 permission definitions, and the approved initial role-permission relationships are seeded.

The design intentionally uses portable relationships, text identifiers, explicit join tables, constraints, and indexes so a later PostgreSQL migration is controlled and straightforward. A later migration will still require planned type conversion and deployment work; it is not automatic.

## Company model

There are two user populations in one `users` table:

- `internal`: employees of the service provider.
- `client`: employees of a client company.

The separation is enforced through assignments and application services:

```text
users
├── internal_user_roles ──────────────── roles
├── employee_client_assignments ──────── clients + roles
├── client_memberships ───────────────── clients + roles
├── user_permission_overrides ────────── permissions + optional client
└── sessions

roles ── role_permissions ── permissions

users + clients ── audit_logs
```

An internal employee has one provider-wide role and can have one separate role for each assigned client. A client employee belongs to one client company and has one role in that company.

## Tables

| Table | Responsibility |
| --- | --- |
| `users` | Login identity, optional username, and password hash for internal and client employees |
| `clients` | Client-company records |
| `internal_user_roles` | Provider-wide role for an internal employee |
| `employee_client_assignments` | Internal employee access and role for each assigned client |
| `client_memberships` | Client employee's company and role |
| `roles` | Named permission groups for internal or client audiences |
| `permissions` | Canonical resource and action pairs |
| `role_permissions` | Permissions included in a role |
| `user_permission_overrides` | Explicit user grant or restriction, globally or for one client |
| `sessions` | Hashed database-backed login sessions |
| `audit_logs` | Access changes, important outcomes, and denied attempts |

## Authorization representation

Permissions are stored as unique `resource + action` pairs. The canonical resources, valid actions, and scope metadata are defined in `src/lib/rbac` and documented in `PERMISSIONS.md`. Canonical permission records and the approved starting role relationships are seeded additively; authorized later changes are not removed when the seed is rerun.

A user's effective authorization will be evaluated in this order:

1. Valid session and active user.
2. Valid internal assignment or client membership for the requested client.
3. Matching user restriction: deny.
4. Matching user grant: allow.
5. Matching permission from the applicable role: allow.
6. No match: deny.

User overrides support:

- Provider-wide scope when `client_id` is null.
- One-client scope when `client_id` is set.
- `grant` or `restriction` effects.
- Optional expiry and reason fields.
- The administrator who created the override.

Partial unique indexes prevent duplicate global and client-scoped overrides.

The Admin Console manages role-permission relationships and overrides without changing the schema or inventing permission names. Successful changes and revocations are audited. Expired overrides remain in the database for administrative history but are ignored by authorization decisions.

## Portability decisions

- IDs are application-generated UUID strings rather than SQLite auto-increment integers.
- Timestamps are UTC ISO-8601 text generated by the application. Their lexical order matches chronological order.
- Role names, permission resources, actions, and statuses are relational columns rather than JSON.
- Boolean-like lifecycle concepts use explicit status values.
- Foreign keys declare update and delete behavior.
- Core uniqueness and lookup paths have indexes.
- SQLite-specific behavior is limited to the driver connection, foreign-key enforcement, and WAL mode.

For PostgreSQL, UUID text columns can become native `uuid` columns and timestamp text columns can become `timestamptz` through an explicit migration.

## Constraints and lifecycle

- Emails must be lowercase and globally unique.
- Usernames are optional, lowercase when present, and globally unique.
- Users are invited, active, or disabled.
- Clients, assignments, and memberships are active or inactive.
- An internal employee can have only one assignment for a given client.
- A client employee can have only one client membership.
- Roles cannot be deleted while they remain assigned.
- Session tokens are stored only as unique hashes.
- Access changes and denied access attempts can retain their audit history even if an actor or client is later removed.

Normal user, client, assignment, and role removal should use status changes rather than hard deletion.

Cross-table rules—such as requiring an internal assignment to reference an internal user and internal-audience role—will be enforced by the authorized application service. They are intentionally not implemented as SQLite triggers because triggers would couple the schema to SQLite and complicate PostgreSQL migration. The authorization layer must deny access if these relationships are inconsistent.

## Confirmed assumptions used by the first migration

Please confirm these schema assumptions:

1. Each internal employee has one provider-wide role.
2. Each internal employee has at most one role per assigned client, and that role may differ by client.
3. Each client employee belongs to exactly one client company.
4. `Owner` and read-only `Employee` are the initial client roles.
5. “Company Secretary” is the intended spelling.

The canonical permission vocabulary and initial role matrix are approved and seeded. The seed is additive and idempotent: rerunning it inserts missing canonical records and demo relationships without resetting existing bootstrap passwords, replacing roles or relationships, or deleting later access changes.
